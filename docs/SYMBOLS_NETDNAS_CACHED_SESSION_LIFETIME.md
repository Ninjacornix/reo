## Reference and expiry interpretation

The basicD0-byte object is a cached session; connection/session-driver objects own it through B0. These pointers are distinct from the protocol-private50/54 fields and the parent hash1C. Retaining through710730 and releasing through728B90 depend on the external counter provider, so a successful-looking pointer lookup is not upgraded to a proven reference-count invariant under arbitrary callbacks.

Lookup728668 rejects expiry only when the time comparator returns exactly-1. Sweep callback728F00 removes when it returns0ornegative. Missing or alternate time providers can return0 without filling destinations, as documented in EXTERNAL_TIME_PROVIDERS. Therefore these paths have different local equality/failure behavior; no actual expired-session incident or clock failure was measured. Several lookup mismatch/codec failures return0 before the later common retain/expiry path, and provider-owned payload retention on those failures remains unresolved.

Cache insertion uses a hash child whose NULL return can mean either a fresh insertion or allocation failure. Its local fresh-entry path still links/retains the session. This is an observed dependency ambiguity, not proof that a live cache is corrupt. Capacity eviction's initial capacity/count tests and post-removal loops were read in full, including the possibility that callbacks alter cache state.

The two linked-list helpers operate only on C4/C8 and parent28/2C. No encoded region was assigned list semantics; complete owned instruction flow supports these entries independently. Extra-data registration and destruction callbacks may reenter application code, which is not simulated here.
