# SNAP packet copying and record-header byte order

Static File #1 US research, 2026-11-04. Full original main-ELF bodies checked against owned words and the [central identity](FUNCTION_INDEX.md). Connects [packet capacities](SYMBOLS_SNAP_PACKET_BUFFER_AND_RETRY_FIELDS.md) with the [poll receive boundary](SYMBOLS_NETWORK_PLATFORM_WORKER_AND_POLL.md). No socket, game, build, attachment or malformed-input test was run.

Addresses, field offsets and status codes are hexadecimal. Protocol records have a16-byte header: two16-bit words and three32-bit words. Low10 bits of the first host-order halfword are a record length. Exact original message enums remain unresolved.

The receive walker validates record lengths after converting a temporary header, while the outbound walker uses the unvalidated length to advance. A zero outbound length can leave both remaining bytes and next pointer unchanged for a valid nonempty packet. Establishing whether such input is constructible is still required before claiming an observed loop or adding a fix.

The header pointer test's actual mask is retained even though an alignment interpretation might seem familiar. Similarly, append capacity checks and copied byte counts use different widths in1F357C. These are static contracts with unresolved producer admission, not reproduced bugs or slowdown diagnoses.
