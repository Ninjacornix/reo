The slab header fields follow their complete consumers: next+0, page/data base+4, u16 slot bytes+8, exponent+A, remaining+C, initial/total slot count+E, free bitmap+10. The initial count is `pageBytes >> classExponent` truncated into16 bits. Available bitmap words are initialized to all ones for complete groups of32; residual bits are set individually by read/OR/write, without a local prior clear of that residual word. Zero initial storage therefore cannot be assumed from this body alone. Inline metadata reserves `ceil(headerBytes/slotBytes)` bits by repeated subtraction, decrementing both halfword counts. The two initial loop conditions were checked; zero tail counts do not imply an unconditional32-bit bitmap iteration.

The map7928AC serves both class-list indexing and page-index lookup in these routines; neither index range is reconstructed from private build data. The scan for a free bitmap word has no independent length check and relies on the class head invariant. The bit scan starts at mask1 and index0, shifting until a set bit is found; the later address computes `(bitmapWordOffset-16)*8 + bitIndex`, then shifts by the stored exponent. This is slot arithmetic, not an arbitrary-input validated API.

The optional fill uses resident107C68(buffer,0xD0,length), whose complete fill semantics are documented separately. Counter additions and high-water comparisons are literal32-bit operations. No synchronization is present in these three clear bodies; caller serialization and protected release/reclamation behavior remain outside scope. All381 owned instruction comments match original bytes, with no omitted nonzero aligned words.
