## Virtual filesystem API and device registry

A file wrapper is two words: interface pointer at +0, backend handle at +4.
The registry at 0x262068 has 32 entries of 16 bytes; each pairs an interface
pointer with name bytes. The 40-slot wrapper pool at 0x261F28 has 8-byte records.
These layer boundaries distinguish an original virtual method from a host file
operation. Some diagnostic paths continue after invoking the error callback;
assuming the callback never returns or that every null path is safe is unsound.

### Polling and units

The scenario-member loader's 0x129C08 result is now identified as a sector-count
API by its own ADXF_GetFsizeSct diagnostic and instruction arithmetic. Multiplying
by 2048 gives a sector-sized quantity, not proof of exact unpadded asset bytes.

0x129D48 is a signed-byte getter. A tight loop calling it does not itself drive
completion. 0x129468 explicitly sets status 2 for an admitted transfer and 3 for
zero work; further completion transitions require following the worker/server
paths. This is useful evidence for later lock/progress measurements, not proof
of a deadlock or a new slowdown reproduction. The virtual filesystem layer also
returns status 3 on some invalid-handle paths; distinguish the layers.

### Single-request ownership

This layer's creator returns only the singleton 0x21BB88. Its null return can
mean that the shared request is occupied even while upper-layer handle pools
have free entries. Disc and host requests occupy different fields of the same
0x38-byte record. That is concrete original serialization, not proof that all
host storage must remain synchronous or that independent reads can safely be
parallelized without validating ordering and callback ownership.

The status getter at 0x137608 is passive. In contrast, stop/wait paths can pump
servers or wait for SDK callbacks. Distinguish passive polls, busy delays,
blocking SDK calls and actual progress work in any later incident diagnosis.
